## 工作包 #1：实施规格

- **目标**：将“首个成功 claim”设为全局 GPU device/backend 锁定点，并以纯状态协调器表达 claim、fallback、resource-ready 的合法转移。
- **依据**：当前 `ensureInitialized()` 会在 claim 前创建 `PipelineCache`、`TextTextureCache`、`CommandBuffer` 与 renderer；`DeviceManager::claimWindow()` 在任意 claim 失败后均会 `cleanup()` 并切换 device；`update()` 在 claim 失败后仍调用 `createPipeline()`，且 white texture 只检查 device/pipeline 指针，未检查窗口 claim/resource-ready。
- **只允许触达**：
  - `src/managers/DeviceManager.hpp`
  - `src/systems/RenderSystem.hpp`
  - `src/systems/render/RenderSystemImpl.hpp`
  - `src/systems/render/RenderBackend.cpp`
  - `src/systems/render/RenderFrame.cpp`
  - 新增一个 `tests/unittest/test_DeviceClaimState.cpp`（或在既有纯状态生命周期测试中新增等价用例）
  - 条件允许 `tests/unittest/CMakeLists.txt`，仅用于登记新增测试源文件，不得调整 target、依赖或编译选项
- **禁止**：公开 `include/` API、其他 manager/renderer、WP7 重构、完整 SDL/GPU API mock、新依赖、GPU 资源抽象扩张、无关重命名/格式化、Git 操作。
- **实现约束**：
  1. 首个窗口 claim 前不得创建 pipeline/cache、command buffer、white texture、纹理缓存或其他持有当前 device/deleter 的 GPU 资源；非 device-bound 字体数据加载可保持现状。
  2. 首窗允许按现有 backend 顺序 fallback；只有成功 claim 后才提交并锁定 device/backend，再初始化 device-bound 资源。
  3. 已有任一成功 claim 后，新窗口 claim 失败只能返回失败并跳过该窗口；不得调用全局 `cleanup()`、销毁/替换 device、切换 backend 或破坏已成功窗口资源。
  4. `update()` 中 claim 失败必须立即跳过当前窗口，禁止继续 `createPipeline()`、创建 white texture、收集 GPU 批次或执行命令。
  5. white texture 只能在当前 device 已锁定、目标窗口已 claim、其余 device-bound 资源 ready 后创建；创建失败不得被标记 ready，也不得继续 GPU 帧。
  6. CPU fallback 只允许首窗尚未锁定且 GPU backend/claim 全部失败时启用；已有成功 GPU claim 后，单个新窗口失败不得把全局后端切为 fallback。
  7. 状态协调测试必须是无真实窗口、无 GPU/SDL API 调用的纯状态测试；覆盖决策与门禁，不引入函数表或完整 mock。
- **验收条件**：
  - 首 claim 前断言 `deviceResourcesReady == false`，且 pipeline/white texture 创建动作不可达。
  - 首窗首次 backend claim 失败、后续 backend 成功时，仅在成功后锁定一次并允许资源创建。
  - 首窗所有 backend 均失败时允许选择 CPU fallback，且不遗留 GPU device-bound 资源。
  - 锁定后第二窗口 claim 失败时，device/backend identity 与既有 claimed-window 集合保持不变；无 cleanup/recreate/fallback 动作。
  - `update()` claim 失败分支不会调用 pipeline 创建；white texture 在 claim 成功且 resource-ready 前不可创建。
  - 重复 claim 已成功窗口保持幂等；unclaim 最后窗口不等价于解锁或自动重建设备，本批不新增重选策略。
  - 交付报告列出所有变更文件、状态转移表及每条验收条件对应测试；静态自检不得遗留已知 error/warning。
- **失败升级条件**：若必须修改公开 API、其他 manager/renderer、引入完整 GPU mock、定义 device 解锁/热切换策略、改变多窗口全局 backend 语义，或现有资源构造无法在允许文件内延后，则停止扩展并回报用户。
