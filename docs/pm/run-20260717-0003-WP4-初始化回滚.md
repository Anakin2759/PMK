## 当前代码核验结论

1. `RenderSystem::ensureGpuResourcesInitialized()` 位于 `src/systems/render/RenderBackend.cpp`，当前按固定线性顺序创建 `PipelineCache`、`TextTextureCache`、`CommandBuffer` 和 renderer；最后仅检查指针非空便将 `DeviceClaimState` 标记为 resources ready。
2. `PipelineCache::loadShaders()` 当前返回 `void`。着色器缺失或创建失败只记录日志，`PipelineCache` 指针仍非空，因此后续 manager 仍会创建，最终可能错误进入 resources-ready 状态。
3. `PipelineCache::loadShaders()` 仅有一个生产调用点，即 `RenderBackend.cpp`；将其改为内部 `Result<void>` 不会扩散到公开 API，也不要求修改所有资源 manager。
4. `RenderSystem::cleanup()` 已按“资源先于 `DeviceManager::cleanup()`”清理，并复位 `DeviceClaimState`，但初始化过程没有统一的失败事务；失败与正常 cleanup 的逆序规则仍散落在成员 reset 顺序中。
5. `DeviceClaimState` 只表达 device lock/resources ready，不记录初始化节点，也不应继续承载资源所有权回滚职责。
6. 当前初始化依赖是单一、固定顺序，不存在运行时分支依赖图；为所有资源建立通用 DAG、拓扑排序、节点注册表或类型擦除执行器属于过度设计。

## 范围决策

### `PipelineCache::loadShaders()` 是否需要返回 `Result`

**结论：本批需要，但只做最小内部改签。**

- 返回 `Result<void>` 是让现有真实失败点可被事务边界观察的最小改动。
- 失败码复用现有 `UiErrc::SHADER_COMPILE_FAILED`；上下文保留驱动名或失败资源信息，不新增错误码。
- `loadShaders()` 在 vertex/fragment 任一失败时返回失败；已创建的局部/成员 shader 必须在退出前清空或随尚未提交的局部 `PipelineCache` 析构，不能留下半初始化 cache。
- 不修改 `createPipeline()`、资源提供器公开契约或其他 manager 的返回类型；不开展全项目 bool/void 到 `Result` 的迁移。

### 如何避免通用 DAG

本批只引入一个 **固定节点、线性顺序、纯逻辑** 的内部初始化事务/状态对象：

`PipelineCache -> TextTextureCache -> CommandBuffer`

- 节点使用闭合集合枚举，不支持动态注册、依赖边、拓扑排序、并行初始化或跨模块插件。
- 状态对象只记录“本次已经成功提交到 `RenderSystemImpl` 的节点”和事务阶段，不拥有 SDL/GPU 对象。
- rollback/shutdown 通过固定逆序访问：`CommandBuffer -> TextTextureCache -> PipelineCache`。
- renderer 创建不是本批 GPU owner 节点：它继续由现有 `initializeRenderers()` 管理；若其构造抛出，先清空可能的部分 renderer，再回滚上述三个已提交节点。不得为此把 renderer 工厂全面事务化。
- `IconManager`、`ImageManager`、`FontManager`、white texture、fallback backend 和 device 不纳入本次事务：它们分别在此前创建、按帧延后创建或属于外层 shutdown，强行纳入会越界到 WP7/完整资源 DAG。

### 固定事务对象规格

1. 类型位于内部命名空间（建议 `ui::systems::render`），只依赖标准库；头文件不得 include SDL、EnTT、manager 或 Runtime/logger。
2. 节点闭合集合仅包含 `PIPELINE_CACHE`、`TEXT_TEXTURE_CACHE`、`COMMAND_BUFFER`，顺序固定。
3. 最小状态至少区分 idle/in-progress/ready/failed/shutdown，或提供等价且可验证的状态语义。
4. 仅在一个节点完整构造并提交给 `RenderSystemImpl` 后记录成功；不得把“准备创建”记作成功。
5. 完成前失败时，以固定逆序对已记录节点各清理一次；清理后节点记录为空，并保留 failed 语义，禁止每帧无界自动重试。
6. 正常 cleanup 使用同一逆序 shutdown 入口；首次 shutdown 清理已记录节点，后续调用不得再次访问这些节点。
7. 清理 visitor/callback 抛出时不得中断剩余节点清理；纯逻辑边界须为 `noexcept` 或在内部吸收异常。测试应验证“中间清理抛出仍继续逆序清理”。
8. 不把 manager 指针、device、窗口或 logger 存入事务对象；生产所有权继续留在 `RenderSystemImpl`。

### 生产接入规格

1. `RenderSystemImpl` 新增事务状态成员；继续保留 `DeviceClaimState`，两者职责不得合并。
2. `ensureGpuResourcesInitialized()` 只在 device 已锁定、资源未 ready、事务允许首次开始时执行。
3. 每个 manager 先在局部 `unique_ptr` 中完成可失败构造/初始化，再移动提交至 `RenderSystemImpl` 并记录节点，避免事务记录半成品。
4. `PipelineCache::loadShaders()` 改为内部 `Result<void>`：无 device、资源读取失败、vertex/fragment shader 创建失败均返回明确错误；调用方必须检查结果。
5. 任一步返回失败或构造抛出时：记录一次错误；清空部分 renderer（若已开始创建）；调用事务逆序 rollback；不得标记 resources ready；不得继续创建后续节点。
6. renderer 成功建立且三个固定节点均成功后，才同时完成事务并调用 `DeviceClaimState::MarkResourcesReady()`。
7. failed 状态下后续 `ensureGpuResourcesInitialized()` 直接返回，避免逐帧重复创建和日志风暴；恢复只发生在完整 cleanup/新 `RenderSystem` 生命周期，不增加运行时重试 API。
8. `RenderSystem::cleanup()`：先清理 backend、等待 GPU idle、清理纹理/renderer 等现有外层资源；随后通过事务 shutdown 逆序 reset 三个节点；最后继续清理其余 manager 和 device，并复位 `DeviceClaimState`。同一事务节点不得在事务入口外重复 reset。
9. 若初始化从未开始或已经失败回滚，cleanup 仍安全；析构触发 cleanup 后再次显式/移动赋值 cleanup 也不得二次清理事务节点。

### 工作包 #1 验收条件

- `loadShaders()` 的失败不再只写日志；`RenderBackend` 能观察并停止后续初始化。
- 任一固定节点失败时，只清理此前已提交节点，顺序严格相反，失败节点的局部半成品由局部 RAII 回收。
- 失败后 `AreResourcesReady()` 保持 false，后续 ensure 不自动重试。
- 成功路径仅在三个节点及 renderer 全部成功后标记事务 ready 和 device resources ready。
- 正常 cleanup 与失败 rollback 使用同一固定逆序状态机制；重复 cleanup 对事务节点为 no-op。
- 新测试仅使用整数、枚举、vector 和 fake callback/visitor，不构造 `UiRuntime`、窗口、device、manager，不调用任何 SDL/GPU API。
- 纯逻辑测试至少覆盖：完整成功顺序、在第 1/2/3 节点失败、逆序回滚、失败后禁止重试、未开始 shutdown、ready 后 shutdown、重复 shutdown、cleanup callback 抛出后继续。
- 交付报告必须列出全部变更文件并逐条映射验收条件；若无改动或受阻，明确原因。

### 工作包 #1 失败升级条件

出现以下任一情况立即停止扩展并回报用户：

- 必须修改公开 API、`DeviceManager`、GPU wrapper 或 renderer 接口；
- 必须引入 shared device lease、完整 GPU mock、通用 DAG、动态节点注册或新依赖；
